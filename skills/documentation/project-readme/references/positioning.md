# README Positioning

Use when the user asks for market positioning, the repo names alternatives, or public incumbent projects are obvious enough to compare without guessing.

## When To Compare

- Include a comparison only when it helps the primary reader choose this project.
- Prefer repo-named alternatives from docs, tests, issues, package descriptions, or examples.
- Use external research only when needed and cite every public comparison source with links.
- Skip comparison when alternatives are unclear or claims would be speculative.

## Section Patterns

- `Why this project`: concise value framing grounded in repo evidence.
- `How it compares`: small table or bullets comparing supported capabilities, target audience, install path, or integration style.
- `When not to use it`: useful when it prevents misuse or clarifies scope.

## Claim Rules

- Avoid claims such as "fastest", "best", "most complete", "production-ready", or "drop-in replacement" unless evidence proves them.
- Prefer factual contrasts: supported platforms, public API shape, dependency footprint, deployment model, file format, license, or documented workflow.
- Do not criticize competitors. State differences that are useful to the reader.
- Keep marketing copy subordinate to setup, usage, and reference clarity.
